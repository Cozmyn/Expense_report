## Phase 1 — findings / constatări

- Critical: no explicit approved ERP-generated-versus-explicit VAT model or model-aware balancing validator. Raw A:X totals must not be treated as a complete ledger. Existing source-like vendor/clearing rows need real interface confirmation.
- High: PostingResult is string rows plus configuration version; no stored typed source-component/FX/policy-linked posting-line entities or readable per-line strategy. Batch stores row JSON/hash but lacks full posting provenance.
- High: request-key idempotency exists, but a different request key after a lost response does not return an equivalent existing batch; current active-export guard rejects it.
- High: columns A/D/F/G/I/P/W/X accept configuration strings without a complete approved per-column type/requiredness contract. Do not invent default dimensions/dates.
- High: PDF ACCOUNTING-only access conflicts with existing Finance export plus Auditor downloads. Owner decision needed.
- High: foreign vehicle split and fuel/repair 50% rules need approved per-branch policies. Current source-style implementation is not proof of ERP/legal correctness.
- Medium: existing preview is a wide table without full source/mapping trace; existing Finance queue/analytics are not the specified accounting batch dashboard.
- Existing safeguards: Serializable request transaction, current manager/Finance checks, accepted calculation checks, production acceptance gate, private immutable export bytes, integrity hashes, values-only24-column XLSX, audit, explicit void/external reversal and preserved manager approval for FX.

Front office: generated journals should remain read-only; errors should link to the offending receipt/source field, and a report must not silently lose populated rows. Back office: replace context-poor A:X-only review with summary→traceable lines→original, approved contract, reconciliation exceptions and historic batch navigation. All changes need RO/EN, keyboard-accessible responsive states.

2. **Contract/design — Accounting/ERP, Back-office UX, Security:** resolve questions; approve posting branch/column contracts, Finance permissions and versioned policy. Deliver guided Finance settings and journal-review design.
3. **Backend — Architect, database, financial engine:** pure typed posting generator; stable IDs; immutable normalized posting lines; additive migrations/constraints; model-aware balancing; stale/review hash checks; business-key retry; correction lineage; scoped dashboard API.
4. **Interface — Back-office/front-office UX, RO/EN content:** contract/mapping review, line preview→source, accept/reject tied to hash, batch history/downloads, accounting dashboard and actionable errors. Employees cannot edit generated journal fields.
5. **QA/release — QA, Security, Product Owner:** ERP-001–014 adapted to owner decisions; deterministic fixtures and reference XLSX; both databases; desktop/mobile; regression/migration/security/role/retry/stale/balance tests; updated API, architecture, guides and matrix.
